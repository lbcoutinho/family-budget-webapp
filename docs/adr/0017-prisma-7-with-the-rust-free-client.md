# ADR-0017 — Prisma 7 with the Rust-free client

**Status:** Accepted
**Date:** 2026-07-27

## Context

ADR-0002 chose Prisma as the ORM without pinning a major. M1 shipped on Prisma 6 (`6.19.3`), and
the M1-close dependency review deliberately held it there: Prisma 7 was already out, works on
Node 24 (ADR-0016), but is a breaking major that reshapes exactly the scaffold M2-T01 is about to
write. M2-T01 (issue #17) therefore carries a pre-work item: decide the major **before** the first
schema and migration exist, because that is the cheapest moment to change it.

Release state at the date of this ADR:

| | Latest | First released | Notes |
|---|---|---|---|
| Prisma 6 | `6.19.3` (2026-04-01) | 6.0.0, 2024-11-28 | patch-only line; new features land in 7 |
| Prisma 7 | `7.9.0` (2026-07-20) | 7.0.0, 2025-11-19 | 9 minors in ~8 months |

`prisma@7.9.0` declares `engines.node: ^20.19 || ^22.12 || >=24.0`, so Node 24 is supported.

What actually breaks in 7 (verified, not read off a changelog — see "Evidence" below):

1. **`url` is gone from the `datasource` block.** The CLI rejects it outright:
   *"The datasource property `url` is no longer supported in schema files. Move connection URLs for
   Migrate to `prisma.config.ts` and pass either `adapter` for a direct database connection or
   `accelerateUrl` for Accelerate to the `PrismaClient` constructor."* So the project gains a
   `prisma.config.ts`, and `PrismaService` must construct the client with a **driver adapter**
   (`@prisma/adapter-pg`, which pulls in `pg` and `@types/pg` itself).
2. **The CLI no longer loads `.env` by default.** Any `prisma` command fails with
   `PrismaConfigEnvError: Cannot resolve environment variable: DATABASE_URL` unless
   `prisma.config.ts` loads it explicitly (`dotenv`). CI, which exports the variables in the job
   `env:`, is unaffected.
3. **The generator changes from `prisma-client-js` to `prisma-client`**, `output` becomes
   mandatory, and the client is emitted as **TypeScript source into the repo** rather than into
   `node_modules`. The default emit is ESM (`import.meta.url`, `.js` import specifiers), which the
   API — CommonJS, `module: Node16`, `ts-jest` transpiling to CommonJS — cannot consume.
   `moduleFormat = "cjs"` and `importFileExtension = ""` on the generator make it consumable with
   **no change to `tsconfig`, `nest build`, or the Jest configs** (both values are first-class
   generator options: an invalid `moduleFormat` is rejected with `expected "esm" or "cjs"`).
4. **Imports move from `@prisma/client` to the generated path.** `PrismaClient` and the `Prisma`
   namespace (including `Prisma.PrismaClientKnownRequestError`, which
   `PrismaExceptionFilter` catches) come from `src/generated/prisma/client`. Today that is
   **3 files**; once M2–M8 add services, repositories and their tests, it is dozens.
5. **The Rust query engine is gone from the runtime.** Prisma 6 generated a ~20 MB directory
   holding the native `libquery_engine-<target>.node`; Prisma 7 generates 116 KB of TypeScript and
   compiles queries in WASM. The CLI still ships a 22 MB native `schema-engine` binary for
   `migrate`, and the published `@prisma/client` tarball is not smaller (its `runtime/` directory
   is 75 MB in the pnpm store versus 73 MB on 6, because both carry the WASM artifacts for every
   provider). **This is not an install-size win; it is a "no native binary in the deployed app"
   win** — no `libssl`/`binaryTargets` matching when the API is containerized.
6. **The CLI has an AI-agent guardrail.** `prisma migrate reset` detects the agent (`AI_AGENT` env
   var) and refuses: *"Prisma Migrate detected that it was invoked by Claude Code… you are
   forbidden from performing this action without an explicit consent and review by the user"*,
   unless `PRISMA_USER_CONSENT_FOR_DANGEROUS_AI_ACTION` carries the user's verbatim consent. This
   repo is Claude-driven, so the planned `db:reset` script becomes a command the **user** runs.

## Decision

**Adopt Prisma 7 (`^7.9.0`) now**, ahead of M2-T01 and before the first migration exists, as a
standalone upgrade so that ticket starts on the final toolchain and its diff is only the `User`
model. The upgrade consists of:

- a `prisma.config.ts` in `apps/api/` holding the datasource URL and the migrations path (M2-T02
  adds the seed command there), loading `.env` explicitly via `dotenv`;
- the `prisma-client` generator emitting to `apps/api/src/generated/prisma`, with
  `moduleFormat = "cjs"` and `importFileExtension = ""`, so the API stays CommonJS and no
  `tsconfig`/Jest/`nest build` setting changes;
- the generated directory **git-ignored** and excluded from ESLint, Prettier and Jest coverage —
  it is regenerated by the existing `postinstall` hook, and the same "never hand-edit generated
  code" rule as `packages/api-client` (ADR-0004) applies;
- `PrismaService` constructing `PrismaClient` with `new PrismaPg({ connectionString })` from
  `@prisma/adapter-pg`, reading `DATABASE_URL` through `ConfigService` so the boot-time env
  validation (M1-T03) remains the single source of truth for configuration.

This ADR complements ADR-0002 rather than superseding it: the ORM choice does not change, only its
major and the client architecture.

## Alternatives considered

| Alternative | Why it was rejected |
|---|---|
| Stay on Prisma 6 for M2 and upgrade later | The `datasource`/config/adapter work is a fixed one-time cost, but the import rewrite scales with the codebase: 3 files today against every service, repository and spec later. Migrations are plain SQL and survive the upgrade, so deferring is possible — it is just strictly more churn, paid at a worse moment |
| Stay on Prisma 6 indefinitely | 6 is a patch-only line; every new feature and fix lands in 7, and each milestone widens the gap |
| Prisma 7 with the legacy `prisma-client-js` generator | It still generates on `7.9.0`, so it would shrink the diff, but it is the superseded path — it would mean adopting the breaking major and then migrating the generator a second time |
| Prisma 7 with the default ESM emit | Would force `module: ESNext`/`moduleResolution: bundler` on the API, an ESM `nest build`, and ESM Jest — a far larger blast radius than the ORM upgrade, for no benefit to a server-side CommonJS app |
| Wait for 7.10 / a later minor | 7.x has had 9 minors over ~8 months and the spike is green end-to-end; waiting only moves the import rewrite past the point where it is 3 files |

## Consequences

### Positive
- The breaking change is absorbed while the API has 3 Prisma imports and zero migrations
- No native query-engine binary in the deployed app: no `binaryTargets`/`libssl` matching when the
  API is containerized, and no engine child process at runtime
- Connection handling becomes explicit and testable — the adapter takes a connection string from
  `ConfigService`, so the client honours the same validated env as the rest of the app
- The generated client is TypeScript the project can actually read when a type is puzzling
- The project stays on the line that receives features and fixes
- The CLI's agent guardrail is a real safety net for a Claude-driven repo: no agent can reset a
  database without the user's explicit, quoted consent

### Negative
- Two new dependencies (`@prisma/adapter-pg` at runtime, `dotenv` for the config file), and one
  more config file to keep in sync with `.env`
- `PrismaService` gains a constructor and a `ConfigService` dependency, so any test instantiating it
  must provide one
- Generated TypeScript now lives inside `src/`, which means new entries in `.gitignore`,
  `.prettierignore`, the ESLint `ignores` list and Jest's `collectCoverageFrom`
- `pnpm --filter api db:reset` can no longer be run by Claude; the user runs it (or exports
  `PRISMA_USER_CONSENT_FOR_DANGEROUS_AI_ACTION`)
- Prisma 7 examples and answers are still thinner on the ground than Prisma 6's

### Risks and mitigations
- **TS2742 in pnpm monorepos** (`cannot resolve @prisma/client-runtime-utils types`, prisma#28581)
  → not reproduced in the spike, because the API compiles with `declaration: false`. If it appears,
  add `@prisma/client-runtime-utils` as an explicit dependency of `apps/api`
- **A WASM query compiler is a different performance profile than the Rust engine** → not measured;
  the app is single-user and single-instance, and if a query path ever matters it is measurable then
- **`prisma.config.ts` and `prisma/seed.ts` sit outside `tsconfig.include`** (`src/**/*`,
  `test/**/*`), so typed ESLint fails on them with *"was not found by the project service"* and
  `tsc` never checks them → widen `include` to cover both as part of the same ticket
- **`tsx` runs `prisma/seed.ts` as CommonJS**, so top-level `await` fails with *"Top-level await is
  currently not supported with the 'cjs' output format"* → keep the seed in a `main()` function
  (M2-T02 writes the real seed)
- **A future Prisma major breaks again** → the surface is now `prisma.config.ts`, `PrismaService`
  and generated-code imports; recorded here so the next upgrade knows where to look

## Implementation

Carried out in the upgrade PR that accepts this ADR — no `User` model, no migration, so the
toolchain change stays reviewable on its own.

1. **Packages.** `apps/api`: `prisma` and `@prisma/client` to `^7.9.0`, `@prisma/adapter-pg` added
   as a runtime dependency (it brings `pg` and `@types/pg`), `dotenv` as a dev dependency for the
   config file.
2. **`apps/api/prisma.config.ts`** holds the schema path, the migrations path and the datasource
   URL, loading `.env` from both `apps/api` and the repo root. The URL is
   `process.env.DATABASE_URL ?? ''` rather than the `env()` helper from `prisma/config`: `env()`
   throws when the variable is missing, and `postinstall` runs `prisma generate` on a fresh clone,
   before anyone has copied `.env.example`. Generating needs no database; the commands that do —
   `migrate`, `studio` — still fail on their own with a clear error. CI needs neither path, since
   the workflow exports the variables at job level.
3. **`apps/api/prisma/schema.prisma`:** `url` dropped from `datasource`, generator switched to
   `prisma-client` with `output = "../src/generated/prisma"`, `moduleFormat = "cjs"` and
   `importFileExtension = ""`.
4. **`PrismaService`** imports `PrismaClient` from `../generated/prisma/client`, injects
   `ConfigService`, and calls `super({ adapter: new PrismaPg({ connectionString: … }) })`, keeping
   the `$connect`/`$disconnect` lifecycle hooks. `PrismaExceptionFilter` and its spec import the
   `Prisma` namespace from the same generated path. Those three files were the only `@prisma/client`
   importers in the API.
5. **Generated output treated as build output:** `apps/api/src/generated/` added to `.gitignore`,
   `.prettierignore` and the ESLint `ignores` list, and excluded from `collectCoverageFrom`.
6. **`apps/api/tsconfig.json` `include`** widened to `prisma.config.ts` and `prisma/**/*.ts`, so
   `tsc` and typed ESLint cover the config file and the seed M2-T02 will add. Without it, typed
   linting fails on `prisma.config.ts` with *"was not found by the project service"*.

Left to the tickets that own them: the `db:migrate` / `db:reset` / `db:studio` scripts and the first
migration (M2-T01), and `migrations.seed` in the config plus `prisma/seed.ts` (M2-T02). `db:reset`
must be documented as user-run, per the agent guardrail above.

## Evidence

Two rounds. First a spike on a throwaway copy of the repo at `d0e7902` — that one carried a `User`
model, a real migration and a seed, which is how the ticket's own steps were validated ahead of
time:

- `prisma migrate dev --name init_user` created and applied a first migration
- `prisma db seed` ran a `tsx` seed through `migrations.seed`, twice, idempotently
- an integration spec created and re-read a `User` and ran `$queryRaw` through `PrismaService`
- `prisma migrate reset` was refused by the agent guardrail described above, and was not run

Then the upgrade itself, on the real repository under Node 24.18 against a local PostgreSQL 16,
with the generated client produced by `postinstall`:

- `pnpm install` on a tree with no `.env` present: `postinstall` generated the client
- `pnpm -r typecheck` and `pnpm lint` clean, with **no `tsconfig`, Jest or `nest build` changes**
  beyond the `include` widening above
- `pnpm --filter api test` (6 unit specs) and `pnpm --filter api test:e2e` (4 specs, real database)
  both green; `pnpm --filter web test` unaffected
- `pnpm --filter api exec prisma migrate deploy` — the CI step — reported no pending migrations
- `pnpm build` across the workspace, then `node dist/main` booted and `GET /api/health` returned
  `{"status":"ok","db":"up"}`
- `pnpm gen` left `packages/api-client` byte-identical, so the OpenAPI contract is untouched

# Internationalization — design

**Date:** 2026-08-04
**Status:** approved in conversation, pending written review
**Milestone:** M3 (adds M3-T10 … M3-T14)

## Problem

The interface is written in Brazilian Portuguese, and every string is a literal sitting in the
component that renders it — `nav-items.ts`, `route-placeholder.tsx`, `loading-spinner.tsx`,
`page-header.tsx`, the auth screens, `router.tsx`. Roughly 35 strings today. Nothing stops the
next screen from adding thirty more.

Two things follow from that:

1. A second language cannot be added without touching every component.
2. The API speaks English. Its business errors (`This is the last active subcategory…`) are
   already scheduled to be shown verbatim to the user — M3-T08's acceptance criteria say "409
   errors display the backend's specific message". A pt-BR user would read an English sentence.

The goal is a structure that supports pt-BR and en-US now and more locales later, with the
language chosen by the user through the interface.

## Decisions

### D1 — Translation lives in the web client; the API speaks in codes

Every business error carries a stable `code` (`CATEGORY_LAST_ACTIVE_SUBCATEGORY`) alongside its
English `message`. The `message` is for logs and debugging and is never rendered. The web client
maps `code` to a translated string.

The API therefore has no i18n dependency, no `Accept-Language` handling, and no locale files. The
codes also serve tests and any future client — the M8 voice entry included.

**Rejected:** the API localizing through `Accept-Language`. It puts translation in two codebases
and makes every error message a backend deploy.

### D2 — `i18next` + `react-i18next`

Chosen over a hand-rolled dictionary because en-US is meant to be a real, published locale rather
than a placeholder: plural rules, interpolation, lazy-loaded locale bundles and language detection
are wanted eventually, and writing them by hand costs more than the two dependencies.

**Rejected:** `@lingui/react` — smaller bundle, but adds a build plugin and an extraction step for
no benefit at this size.

### D3 — pt-BR and en-US from the first commit

One locale rots: with a single file nobody notices a hardcoded string. Two locales plus an ESLint
rule make a regression visible immediately.

pt-BR is the default and the source of truth for wording. en-US is kept at parity — a key added to
one is added to the other in the same pull request.

### D4 — The preference lives on `User`

`User.locale`, one column, one migration, edited through `PATCH /api/users/me`. Not a
`UserSettings` table: there is exactly one preference today, and a one-row table for one value is
ceremony. When a second preference appears (theme, date format), promoting the column to a table
is a mechanical migration.

`localStorage` holds a mirror, used only before the session is known (the login screen) and to
avoid a flash of the wrong language on boot. It is a cache, never the source of truth.

Resolution order: `User.locale` → `localStorage` mirror → `navigator.language` → `pt-BR`.

### M3-T10 — i18n foundation (web)

- `i18next` and `react-i18next` added to `apps/web`.
- Locale files at `apps/web/src/i18n/locales/pt-BR.json` and `en-US.json`. A single namespace
  until one proves insufficient.
- Keys grouped by domain: `nav.month`, `common.loading`, `errors.<CODE>`.
- `nav-items.ts` stores a key rather than a label; `RoutePlaceholder` takes `titleKey`.
- `lib/money.ts` and `lib/date.ts` keep owning all formatting, but receive the active locale
  instead of a hardcoded `pt-BR`.
- ESLint `i18next/no-literal-string` over `features/**` and `components/**` `.tsx`, with an
  allowlist for non-linguistic literals. Without this rule the structure decays within two screens.
- Existing tests query by accessible name in Portuguese (`getByRole({ name: 'Mês' })`). They
  resolve through the real `i18n` instance initialised to pt-BR in the test setup, so no string is
  duplicated between test and locale file.

### M3-T11 — Error codes

- Business errors respond with `{ statusCode, code, message }`. `code` is SCREAMING_SNAKE and
  listed in one shared enum; `message` stays English and is never rendered.
- Codes existing today: last active subcategory, two-level tree violation, category as its own
  parent, root category without `kind`, duplicate name (P2002), record in use (P2003).
- `PrismaExceptionFilter` emits `code` for the mappings it already performs.
- Web resolves `errors.<CODE>`; an unknown code falls back to a generic translated message and
  **never** to the English `message`.
- M3-T08's acceptance criterion "409 errors display the backend's specific message" is amended on
  issue #52 to mean the translated message for the returned code.

### M3-T12 — `locale` on `User`

- `locale String @default("pt-BR")` on `User`; one migration.
- `PATCH /api/users/me` accepts `locale` only, validated against the supported-locale list.
- `AuthUserDto` carries `locale`, so the application wakes up in the right language without an
  extra request.

### M3-T13 — Settings › General

- **Blocked:** no approved prototype exists. `prototypes/07-settings-general.html` must be drawn,
  reviewed and moved to `prototypes/approved/` before any React is written.
- New nav item **Geral** inside the Configurações group, above Contas and Categorias.
- One "Idioma" section: a `Select` offering Português (Brasil) and English (US), saved
  immediately with a toast. No Save button.

### M3-T14 — Deploy to Vercel

**Do not execute before discussing.** Vercel hosts `apps/web` naturally (a static Vite SPA), but
the API is NestJS + Prisma + PostgreSQL, which is not Vercel's terrain and needs a managed
database regardless. The open question, to be settled at the start of the ticket:

- **A** — Web on Vercel only, `VITE_API_URL` pointing at the API hosted elsewhere (Railway /
  Render / Fly, plus Neon). Keeps Nest on a normal Node runtime; costs two providers plus CORS and
  environment wiring. _Provisional recommendation._
- **B** — Everything on Vercel: static web, Nest as a single serverless handler, Postgres on
  Neon or Vercel Postgres. One provider and one bill; pays for it with Nest cold starts and
  Prisma connection pooling in a serverless runtime.
- **C** — Web on Vercel against mocks, no real API, as a showcase deploy until M5 delivers visible
  value.

## Out of scope

- Localizing the API.
- Locales beyond pt-BR and en-US.
- Localized number and date _formats_ beyond what `Intl` already gives through the active locale;
  the single-currency rule (euro) is unchanged.
- Right-to-left support.
